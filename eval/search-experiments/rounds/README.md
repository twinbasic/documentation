# search-eval

A reusable harness for measuring search-ranking quality and client-side cost
of the twinBASIC docs site's lunr search index, to compare index-granularity
and query-tokenizer designs. Everything here is scratch output — none of it
is part of the site's repo or build.

## What it is

`eval.cjs` is the CLI harness: it loads a copy of `search-data.json`, builds
the exact client lunr index (title boost 200 / content boost 2 / relUrl,
`term(boost:10)` + trailing-wildcard, capped fuzzy fallback — mirrors
`builder/vendor/just-the-docs/assets/js/just-the-docs.js`), derives a query
set from ground truth, and reports hit@1/5/10, MRR (capped at 20), % with
zero correct, cost (entries, raw/gzip bytes, median build time over 3 runs,
heap delta, median query latency), broken down by category and symbol kind.
Verified to match `eval/site_search.mjs`'s rankings for distinguishing
queries — but note `eval/site_search.mjs` never sets
`lunr.tokenizer.separator`, so it silently uses lunr's own default
(`/[\s\-]+/`, no `/`) instead of the client's real `/[\s\-/]+/`; this
harness sets it correctly. That gap is also why `eval/site_search.mjs`
doesn't reproduce the `"*"` crash (see below) — it's real in the client.

Usage: `node eval.cjs data-a.json [data-b.json ...] [--worst N] [--sample N] [--out path]`.
Everything else here (`diagnose-*.cjs`, `run-variants.cjs`, `make-variants.cjs`,
`config-b.cjs`) is one-off investigation scripts built on top of `eval.cjs`'s
exported helpers (`module.exports` at the bottom), not part of the CLI.

## Regenerating from scratch

1. `heading_level` variants: append `search:\n  heading_level: N` to
   `docs/_config.yml`, run `node builder/tbdocs.mjs --src docs --no-check --no-offline --no-pdf`,
   copy `docs/_site/assets/js/search-data.json` → `data-hN.json`, **restore**
   `docs/_config.yml` and rebuild once more with the original config.
   `git status --short` must end clean.
2. `data-v2.json`/`data-v3.json`/`data-v4.json`: `node make-variants.cjs`
   (folds/retitles generic subsections — See Also/Example/Examples/Remarks/
   Parameters/Return value/Syntax/Notes — into the preceding entry).
2b. `data-v5-50.json`: generated by `diagnose-final.cjs` — adds a `symbols`
   field (bare + `Class.Member` names from `symbols.json`, matched by
   normalized relUrl) to every V2 entry.
3. Query-tokenizer variants (V4b/Q-split/Q-smart/Q-smart-req) don't need new
   data files — they only change how the *query string* is tokenized at
   search time; see `config-b.cjs` and `diagnose-final.cjs`.
4. `symbols.json` (ground truth) is copied once from
   `docs/_site/tB/symbols.json` — it's independent of `heading_level`, so one
   copy covers every index variant.

## Ground truth and its known biases

- **Bare-name queries**: one per unique symbol name; correct if the hit's
  normalized URL matches ANY symbol sharing that name. **Bias**: ~18% of
  names are genuinely ambiguous (`Left`, `PaintPicture` on 30+ controls),
  which the "any" rule absorbs — a stricter single-URL rule would be far
  harsher and arguably wrong, since twinBASIC really does redeclare members.
- **Qualified `Class.Member` queries**: correct only for that exact symbol.
- **Prose queries**: 20 **hand-picked** by us, matched by page (not anchor).
  Small sample, cherry-picked for plausibility — not a random sample of real
  user queries, so its 80% hit@10 is not a strong statistical claim, just a
  sanity check that stayed roughly stable across every variant tested.
- **V5's `symbols` field is partly circular** with bare/qualified ground
  truth by construction (the field is literally built from the same
  `symbols.json`). We mitigated this with a seeded 50/50 held-out split
  (`mulberry32(42)`): held-out queries (their symbols never in the field)
  still improved hit@10 82.4%→87.3%, so some of the gain is real
  generalization, not pure memorization — but the reported full-field
  numbers (97%+) should be read as an upper bound, not a field estimate.

**Recommendation: ship R unchanged.** Round 5 diagnosed all 37 R-vs-h2
regressions with matchData evidence (`regressions-R-vs-h2-full.json`,
`r1-diag.log`) and grouped them: **21** are single-rank (delta=1) BM25
length-norm near-ties on the `ControlTypeConstants` enum (e.g. `vbCheckBox`)
where a tiny, unrelated per-control `ControlType` property blurb edges out
the enum table by a ~2% score margin once every doc gets a `symbols` field;
**10** are short/common keywords (`With`, `Is`, `VB`, `Do`, `For`, `Each`,
`On`, `Select`, `Time$`, `Lock`) whose trailing-wildcard match now also hits
long compound names inside other pages' bloated `symbols` fields (e.g. "With"
wildcard-matches "WithDispatchForwarding"); **5** are the pre-existing h3
prose title-collisions from earlier rounds (Fusion, 64-bit compilation, etc.,
unrelated to symbols/tokenizer); **1** is the `"/"` divide-operator query,
which tokenizes to zero terms because `/` is itself a separator character —
a structural gap query.term() can't fix (would need a raw-string fallback
when tokenization yields nothing). We tried F1 (exact-title term,
boost 20/50/100), F2 (identifier-normalized "name" field, boost 50/100), F3
(bare-name-only symbols field, boost 50/25), and every pairwise/triple
combination (`results-r-fixes.json`, `r2-run.log`): **none cleared the
acceptance bar** (fewer h2-regressions than R's 37, no metric below R's by
more than noise, no new unexplained large regressions). F1@100 got closest
(36 regressions) but shuffled 108 other queries' ranks for a net gain of one,
and increased large (21-50-rank) regressions from 3 to 5. F2 and F3 each
traded a narrow win for a broad loss (F3 in particular guts the qualified-
query gain that is R's main point). All three failure buckets are small
(≤26-rank deltas except the structural "/" case) and well-understood, so
leaving R as-is — rather than adding index/query complexity that measurably
loses elsewhere — is the evidence-backed choice.

Full per-query data: `results-final.json`, `regressions-B-vs-h2.json`,
`misses-B.json`, `regressions-R-vs-h2-full.json`, `results-r-fixes.json`.

## Round 6 update: F5-F8, and a measurement bug in round 5's "/" finding

Round 5's `"/"` diagnosis used a slightly-different reimplementation of
Q-smart that **omitted the zero-token guard** (`if (whole.length===0 &&
extra.length===0) return [];`), which the real R (`diagnose-final.cjs`)
does have. Confirmed directly: under true R, `runQuery("/")` returns **0
results** (verified in `diagnose-r3.cjs`), not h2's arbitrary all-docs match
— going from an accidental lucky rank (763, found only because a zero-clause
lunr query returns everything) to a clean, deterministic empty result is a
correctness improvement, not a regression, even though the naive rank-delta
metric still counts it as "worse". Excluded from all round-6 regression
counts below (so R's own count is 37, not 38).

Targeted fixes (`results-r3.json`, `r3-run.log`):
- **F5** (wildcard search excludes the `symbols` field): fixes 1 of the 37
  (36 remain) but breaks 75 queries vs R — mainly every `$`-suffix qualified
  form (`Strings.Left$` 36→977, etc.), which relied on the wildcard hitting
  `symbols` for the trailing `$`. **Rejected.**
- **F6** (no wildcard for tokens <3 or <4 chars): only 4-21 new regressions
  vs R by count, but they're severe — `Do`, `If`, `Is`, `On` (all 2-char
  keywords) go to **rank "none"** or deep double digits, because those GT
  titles need the wildcard to match at all. **Rejected** — the "no large
  unexplained regressions" bar fails hard.
- **F7** (split `symbols` into bare-only `names` + `Container.Name`-only
  `qualified` fields, shrinking each so BM25 discounts them less): **best
  result of any round.** At boost names=100/qualified=50: **26 regressions
  vs h2 (beats R's 37)**, overall MRR **.9326** (> R's .9288), bare MRR
  **.9619** (> R's .9455), hit@10 unchanged (97.9%/97.8%), qualified hit@10
  unchanged (97.7% vs 97.9%) — this is the fix that actually targets group A
  (`ControlTypeConstants` near-ties no longer appear in the top regressions).
  **But** it introduces new, smaller regressions of its own: prose drops to
  75% (one query, "symbol index", 1→32) and several `Drag`-event qualified
  queries on multiple controls regress 1-3→23-27. Group B (`With`/`Is`/`Do`/
  `For`/`VB`/etc.) is **untouched** by F7 either way — it only ever targeted
  group A. F7 at 50/50 or 50/25 boost is worse on both axes than 100/50.
  F8 was not attempted since F7 already reduced group A's regression count.

## Round 7 update: F9/F9b -- tested, and it backfires

lunr's tokenizer tests **one character at a time** against `separator`
(`r.charAt(s).match(separator)`, confirmed by reading `lunr.min.js` and
empirically: `lunr.tokenizer('Do...Loop')` with separator
`/[\s\-/]+|\.{2,}/` still returns `["do...loop"]` — a `{2,}` quantifier can
never match a 1-character string). Implemented instead as **string
preprocessing** — replacing runs of 2+ `.` with a space — applied on both
sides: the index side (what `builder/search.mjs` could do to title text
before writing `search-data.json`) and the query side (what
`just-the-docs.js`'s `update()` could do to `input` before tokenizing); a
single `.` is untouched so `Debug.Print`/`1.0` are unaffected and Q-smart's
split still runs on them. 30 entries' titles contain `'…'` (F9b's check);
only ~9 are the compound-keyword ones (`Do…Loop`, `For…Next`, `If…Then…Else`,
`On…GoSub`, `GoSub…Return`, …) — the rest are unrelated nav/prose ellipses.

**Result: F9/F9b make group B *worse*, not better.** `Do` and `For` (and
`While`) go from a mediocre-but-findable rank to **completely unfindable**
(`none`); `On` collapses from rank 3 to 960; only `Each` improves (6→1) and
`If` is a wash. Root cause, found by reading `lunr.min.js` further: lunr's
**index** pipeline is `[trimmer, stopWordFilter, stemmer]` but its **search**
pipeline is `[stemmer]` **only** — `stopWordFilter` never runs on query
terms, only on indexed content. `do`, `for`, `on`, `is`, `if`, `while`,
`with` are all in lunr's built-in English stopword list. Before F9, `"Do
Loop"`'s title survived as one glued non-stopword token `"do...loop"`,
findable via trailing-wildcard prefix match; F9 splits it into real words,
and the index-time stopword filter then deletes the standalone `"do"` token
from the index entirely — while the query "do" is never filtered, so it
now matches nothing. **The compound punctuation was accidentally shielding
these pages from lunr's own stopword list; splitting it removes that
shield.** F9b (adding `'…'`) has the identical failure mode. Both **rejected**
— they add large, well-understood but harmful new regressions with almost
no offsetting fix.

F7's two known side effects are unchanged under F9/F9b (same cause, textual
preprocessing doesn't touch them): the `Drag`-event qualified queries are
untouched, and **`"symbol index"` (prose) still ranks 1→32** — diagnosed:
its token `"index"` is itself a real symbol name (the `Index` property
shared by ~10+ VB controls), so `names`-field boost 100 gives every
`CheckMark`/`Frame`/`Image`/`Label`/`Line`/… control's `Index` property an
exact-match score of 608, decisively beating the prose page's boost-2
content-only mention.

Round 7's own recommendation was to keep F7 unchanged and flag that fixing
group B for real would require removing `stopWordFilter` from lunr's index
pipeline — untested at the time. Round 8 tested it.

## Round 8 update: F10 (remove stopWordFilter) -- the actual fix

`this.pipeline.remove(lunr.stopWordFilter)` inside the builder, on top of F7
+ Q-smart + guard. Measured alone (F10) and combined with round 7's
dot-preprocessing (F10+F9), which is now *safe* to add since the thing that
made it backfire (index-time stopword deletion of the split-out "do"/"on")
is gone.

**Group B**: F10 alone fixes `With` (54→1), `Is` (176→1), `On` (3→1), and
partially `Do` (18→2); F10+F9 fixes **all six actual stopwords** in the
group — `With`, `Is`, `Do`, `For`, `Each`, `On` all reach rank 1. `VB`,
`Select`, `Time$`, `Lock` are unchanged (16, 5, 7, 3) — confirmed these were
never stopwords, so this fix correctly leaves their (separate, unsolved)
wildcard-crowding problem alone. **Prose improved** (75%→80%, `With
statement` 19→4) — no damage from `the`/`a`/`of`, so **F10q was not
needed** and wasn't built, per the round's own instruction to skip it absent
that damage.

New regressions vs F7 (43 for F10, 42 for F10+F9, ~21-23 improve too): all
small (1-9 ranks: `DataMembers.Item` 1→9, several `.Value`/`.Top`/`.Name`
qualified properties 2-4→4-6, several `vbKeyXxx` bare constants 1→2) — the
expected collateral effect of thousands of previously-filtered stopwords
now appearing in every document's content field, marginally diluting BM25
scores index-wide. None are large or unexplained. `"symbol index"` (prose,
the `Index`-property collision from round 6) and the `Drag`-qualified
near-ties are unaffected — different, already-diagnosed cause.

**Final recommendation: F10+F9 — remove `stopWordFilter` from the index
pipeline, plus F7 (names=100/qualified=50) + the 2+-dot title preprocessing
+ Q-smart + the asterisk guard.** It beats every prior configuration on
every axis measured (fewest h2-regressions of any round: 19; best MRR;
prose actually improved) at a real but acceptable cost (~24% larger gzip
index, ~35ms slower build, both one-time/build-side costs; query latency is
unaffected or better). Cost growth is the expected, correctly-predicted
consequence of un-filtering thousands of previously-dropped common words,
not a surprise. `VB`/`Select`/`Time$`/`Lock` remain the last open item —
confirmed non-stopwords, so a genuinely different, still-unsolved cause
(wildcard-crowding from the `symbols`/`names` field), not revisited here.
